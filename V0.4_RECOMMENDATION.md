# V0.4_RECOMMENDATION.md
Print2Go Production OS — Recommendation for V0.4 (AWAITING EXPLICIT APPROVAL)

`REAL_FIERY_BACKEND` stays `NOT_IMPLEMENTED` until you approve V0.4. This document
only recommends an approach; it implements nothing.

## Prerequisite before any write backend
Run the V0.3 Edge Agent on the actual London Windows PC that can reach PX300 and
capture a real capability matrix (replacing all `UNKNOWN`s with evidence). Do not
choose an implementation mechanism until that report exists.

## Recommended sequencing
1. **Confirm mechanism (still read-only).** From the real matrix, pick the highest-
   confidence, lowest-risk integration in this order of preference:
   1. **Fiery API (EFI)** if `REAL_FIERY_API_AVAILABLE = YES` — cleanest, auditable.
   2. **Hot Folders** if API absent — file-drop with server-side preset/impose.
   3. **Command WorkStation automation** only if neither is available (fragile; may
      require GUI automation → mark `GUI_AUTOMATION_REQUIRED`).
2. **Classify "London BC" positively** (IMPOSE_TEMPLATE vs JOB_PRESET vs HOT_FOLDER)
   and confirm it can be applied programmatically and under what license.
3. **Implement IMPORT_TO_HELD only** first (job lands in a HELD queue, never printed),
   behind a feature flag, on a non-production/test Fiery. Verify with VERIFY_JOB_STATE.
4. **Add imposition apply + save** to HELD, still no print/release.
5. Keep the human PRINT gate. PRINT/RELEASE remain out of scope until separately
   approved with physical safeguards.

## Non-negotiable guardrails to carry into V0.4
- Every write action passes the policy engine + allowlist + idempotency + audit.
- All writes target a HELD state; no auto-print, no job release/delete/modify.
- Mock adapter remains impossible to select in `DEPLOY_ENV=production`.
- Host/IP and credentials remain local to the Edge Agent; cloud uses `device_role`.
- No mock success is ever labelled `REAL_WORLD_VERIFIED`.
